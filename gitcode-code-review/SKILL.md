# GitCode PR 代码审查 Skill

## 概述

代码审查 skill 用于自动审查 GitCode 仓库的 Pull Request。本 skill 基于官方 code-review 插件的 9 步流程设计，采用多代理并行审查、独立验证和置信度评分机制，确保只报告高质量的问题。

### 审查维度

1. **Bug 扫描 (仅 diff)** - 扫描明显的语法错误、类型错误、API 误用
2. **代码问题分析** - 查找安全问题、逻辑错误、性能问题、错误处理缺陷
3. **语义深度分析** - 理解代码意图和上下文，发现深层逻辑问题

### 核心特性

- **多代理并行审查** - 4 个代理同时分析，提高效率
- **独立验证阶段** - 对发现的问题进行二次验证，减少误报
- **置信度评分** - 只发布置信度 >= 80 的问题
- **自动去重** - 相同问题只报告一次
- **AI 签名** - 每条评论包含 "generated by ai@claude"

## 9 步审查流程

```
Step 1: 前置检查     → PR 是否已关闭/草稿/已审查？
Step 2: 收集上下文   → 获取 PR 详情、文件内容、CLAUDE.md
Step 3: 总结 PR      → 概述变更内容和目的
Step 4: 并行审查     → 4 个代理同时分析
Step 5: 独立验证     → 对问题进行二次验证
Step 6: 过滤去重     → 移除低置信度和重复问题
Step 7: 判断         → 无问题则发送 summary
Step 8: 准备评论     → 格式化评论内容
Step 9: 发布评论     → 提交到 GitCode PR
```

## 使用场景

当用户需要：
- 审查 GitCode 仓库的 Pull Request
- 自动发现代码中的 bug 和逻辑错误
- 生成高质量的代码审查意见

## 工作流程

### 1. 准备配置

在 `config.json` 中配置 GitCode 认证信息：

```json
{
  "gitcode": {
    "token": "your_personal_access_token",
    "owner": "openeuler",
    "repo": "lerobot_ros2",
    "baseUrl": "https://api.gitcode.com"
  },
  "codeReview": {
    "confidenceThreshold": 80,
    "skipValidation": false
  }
}
```

### 2. 获取 GitCode Personal Access Token

1. 登录 [https://gitcode.com](https://gitcode.com)
2. 点击右上角头像 → 个人设置
3. 找到「访问令牌」选项
4. 创建新令牌，勾选 `repo` 和 `pull_request` 权限
5. 将 Token 填入 `config.json`

### 3. 运行审查脚本

#### 模式 1：生成 prompts 供手动审查

```bash
# 生成各代理的 prompts，保存到 .temp-review/ 目录
node skills/gitcode-code-review/scripts/gitcode-reviewer.js --pr 123
```

执行后：
1. 在 `.temp-review/` 目录生成 4 个代理的 prompt 文件
2. 在另一个 Claude Code 会话中执行这些 prompts
3. 将发现的问题保存为 JSON 文件
4. 使用模式 2 提交评论

#### 模式 2：从 JSON 文件提交评论

```bash
# 从 JSON 文件加载问题并提交到 GitCode PR
node skills/gitcode-code-review/scripts/gitcode-reviewer.js --pr 123 --issues-from-json issues.json
```

#### 跳过验证（快速模式）

```bash
node skills/gitcode-code-review/scripts/gitcode-reviewer.js --pr 123 --issues-from-json issues.json --skip-validation
```

#### 自定义置信度阈值

```bash
node skills/gitcode-code-review/scripts/gitcode-reviewer.js --pr 123 --issues-from-json issues.json --threshold 70
```

### 4. JSON 文件格式

创建 `issues.json` 文件：

```json
[
  {
    "file": "examples/lekiwi/evaluate_dataset.py",
    "line": 15,
    "type": "bug",
    "severity": "error",
    "confidence": 90,
    "title": "Shebang 格式错误",
    "description": "Shebang 缺少 ! 符号，导致脚本无法直接执行",
    "contextCode": "# !/usr/bin/env python\n# 应改为:\n#!/usr/bin/env python",
    "fix": {
      "code": "#!/usr/bin/env python",
      "explanation": "修复 shebang 格式，确保 # 和 ! 之间没有空格"
    }
  }
]
```

**字段说明**：

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| file | string | 是 | 文件路径（相对于仓库根目录） |
| line | number | 是 | 问题行号（在新文件中的行号） |
| type | string | 是 | 问题类型：bug, security, logic_error, api_misuse |
| severity | string | 是 | 严重程度：error, warning |
| confidence | number | 是 | 置信度 0-100，只报告 >= 80 |
| title | string | 是 | 问题标题 |
| description | string | 是 | 详细描述 |
| contextCode | string | 是 | 上下文代码 |
| fix | object | 是 | 修复方案（code + explanation） |

### 5. 审查输出

审查工具会：
1. 计算 position（在 diff 中的位置）
2. 将审查意见作为 **Inline 行内评论** 发布到 GitCode PR（直接附加到代码行）
3. 每条评论包含 AI 签名："generated by ai@claude"
4. **自动添加官方参考资料**：根据问题类型自动添加相关文档链接
5. **输出审查链接**：完成后输出 PR 页面和各评论的链接，方便直接查看和修正

#### 行内评论示例

```
❌ **argparse 中 type=bool 参数无法正常工作**

在 argparse 中使用 `type=bool` 不会按预期工作...

**上下文代码**:
```
parser.add_argument("--verbose", type=bool, ...)
```

**修复方案**:
```
parser.add_argument("--verbose", action="store_true", ...)
```

**官方参考资料**:
- [Python argparse Documentation](https://docs.python.org/3/library/argparse.html)
- [Why type=bool doesn't work in argparse - StackOverflow](https://stackoverflow.com/questions/15008758/...)

---
🤖 generated by ai@claude
```

#### 审查链接输出示例

```

============================================================

📋 审查意见链接:

   - examples/lekiwi/evaluate_dataset.py:101 → https://gitcode.com/.../pull/46#comment-124
```

## 审查规则

### 高信度问题标准

只报告满足以下条件的问题：

1. **编译/解析错误** - 语法错误、类型错误、缺少导入
2. **明确的逻辑错误** - 无论如何输入都会产生错误结果
3. **安全问题** - SQL 注入、XSS、硬编码敏感信息
4. **明显的 API 误用** - 不符合标准用法
5. **严重的错误处理问题** - 空 catch 块、吞掉异常

### 不报告的情况

- 代码风格问题
- linter 可捕获的问题
- 预先存在的问题
- 可能不是问题的地方（不确定时不报告）
- 需要额外上下文才能判断的问题

### 误报防护机制

为减少"变量未定义"等误报，代理必须遵循**三步检查法**：

**第一步：变量定义追踪**
1. 向上搜索：从问题行向上查找变量定义
2. 向外搜索：在函数/方法外查找
3. 作用域分析：判断变量是否在使用点可见

**第二步：变量生命周期分析**
- 循环内定义的变量在循环体内可用
- 外层定义的变量在内层作用域可用
- 注意条件分支中的变量定义

**第三步：数据流分析**
- 追踪变量的值如何变化
- 检查类型转换是否正确
- 验证维度/形状匹配（特别是 tensor 操作）

**典型案例（必须避免）**：
```python
# ❌ 错误判断："shape 未定义"
for key in input_features:                    # 第 45 行
    shape = [1] + list(input_features[key]["shape"])  # 第 48 行定义
    # ... 多行代码 ...
    some_function(shape)                       # 第 60 行使用
```
正确分析：shape 在第 48 行定义，第 60 行使用，作用域正确。

## 常见问题

### Q: Token 无效或认证失败？
A: 请检查：
1. Token 是否正确复制（无多余空格）
2. Token 是否已过期
3. Token 是否有足够的权限（repo + pull_request）

### Q: 审查没有发现任何问题？
A: 这可能表示：
1. PR 代码质量良好，没有明显问题
2. 置信度阈值设置过高，可以尝试降低 `--threshold`

### Q: 如何查看代理的 prompt？
A: 代理 prompt 保存在 `.temp-review/` 目录，文件名格式为 `agent-{N}-{name}.md`

### Q: 审查结果如何提交到 PR？
A: 审查工具会自动将结果作为 Inline 评论提交到 GitCode PR
